# Архітектура MVP

Один Python-застосунок: Streamlit викликає прикладні модулі, вони використовують
чисті фінансові функції, PostgreSQL та один LLM endpoint. Додатковий REST backend,
черги, ORM і агентний фреймворк на першому етапі не потрібні.

## Межі відповідальності

Decimal рахує гроші; PostgreSQL зберігає їх як NUMERIC(18,2). Перетворення на float
дозволене лише для графіка. pandas читає CSV як текст, щоб не втрачати точність.
Імпортер зберігає оригінальну валюту та окрему EUR-суму.

Модель пропонує тип дії, суму, дату, пояснення й ризики. Pydantic перевіряє структуру,
а код окремо перевіряє фінансові обмеження. Валідний JSON не означає правильне рішення.
Агенти не мають доступу до SQL, мережевих інструментів або реальних платежів.
До моделі передаються агрегати, а не IBAN чи довільні призначення платежів.

Поточні агенти — початкові адаптери. Майбутній оркестратор має передавати їм
лише перевірений майбутній горизонт, включно із залишком на початку, та зберігати
версію прогнозу. Перевірки сум не замінюють модель кредитних умов або інвестиційних строків.

## Погодження і стан

Запланований workflow: pending → approved → simulated або pending → rejected.
Погодження має стосуватися незмінного snapshot рекомендації та прогнозу.
Оновлення стану і запис аудиту — одна транзакція з блокуванням рядка та
перевіркою попереднього стану. Повторний клік не може створювати другу операцію.
Зміна вхідних даних вимагає нового прогнозу та погодження.
Streamlit session_state не є джерелом істини для цього workflow.

## Пріоритети challenge

Спершу завершений liquidity use case, потім investment. Умови вимагають щонайменше
одного наскрізного сценарію. Застосунок і open-weights/open-source модель мають
працювати в наданому OpenShift AI. Локальний режим не виконує ці вимоги.
vLLM доцільний як runtime; решта бонусних технологій не потрібна для старту.
